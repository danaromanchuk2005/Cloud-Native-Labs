# Звіт до Лабораторної роботи №8

**Тема:** Безпека, масштабування та оркестрація мікросервісної архітектури з використанням Nginx, Node.js, Go, PostgreSQL та MongoDB

---

## 1. Мета роботи
Спроєктувати та розгорнути захищену відмовостійку мікросервісну систему в середовищі **Docker Compose** з єдиною публічною точкою входу через зворотний проксі-сервер **Nginx**, налаштувати шифрування трафіку (**TLS / HTTP/2**), кешування статичних ресурсів і відповідей API, обмеження частоти запитів (**Rate Limiting**), горизонтальне та вертикальне масштабування бекенд-сервісів, а також посилення безпеки контейнерів (**Container Hardening**).

---

## 3. Реалізовані механізми безпеки та масштабування

### 3.1. Захист транспортного рівня та заголовки безпеки (Nginx)
* Налаштовано автоматичне перенаправлення всіх незашифрованих HTTP-запитів (порт `80`) на HTTPS (порт `443`) зі статусом `301 Moved Permanently`.
* Увімкнено підтримку сучасного протоколу **HTTP/2**, шифрування `TLSv1.2` / `TLSv1.3` та заголовок **HSTS** (`Strict-Transport-Security: max-age=31536000; includeSubDomains`).

### 3.2. Багаторівневе кешування
* **Статичні ресурси (`/static/`):** обслуговуються безпосередньо вебсервером Nginx без навантаження на бекенд із заголовками `Cache-Control: max-age=2592000` та `public, immutable`.
* **Кешування API (`GET /api/catalog`):** реалізовано проксі-кешування (`proxy_cache`) на рівні Nginx з індикацією статусу через кастомний заголовок `X-Cache-Status` (`MISS` при першому зверненні та `HIT` при наступних).

### 3.3. Захист від Brute-Force та надмірного навантаження (`limit_req`)
* Для критичного ендпоінта автентифікації `POST /api/auth/login` налаштовано обмеження частоти запитів. При перевищенні дозволеного ліміту Nginx блокує подальші спроби зі статусом `429 Too Many Requests`, не пропускаючи паразитний трафік до Node.js та баз даних.

### 3.4. Горизонтальне та вертикальне масштабування
* **Горизонтальне масштабування:** Nginx балансує вхідні запити до `/api/` між трьома репліками `node-app-1`, `node-app-2`, `node-app-3` та автоматично виключає недоступні вузли при збоях (`proxy_next_upstream`).
* **Вертикальне масштабування:** сервіси Node.js використовують вбудований модуль `cluster` для паралельної обробки запитів на кількох ядрах процесора, а Go-сервіс автоматично оптимізує `GOMAXPROCS` відповідно до лімітів контейнера за допомогою `go.uber.org/automaxprocs`.

### 3.5. Container Hardening (посилення безпеки образів)
* Використано багатоетапну збірку (**Multi-stage Docker builds**) на базі мінімальних образів `alpine`, завдяки чому у фінальних контейнерах відсутні компілятори, інструменти збірки та кеші пакетів.
* Контейнери запускаються від **непривілейованих користувачів**: `node` для Node.js-сервісів та `appuser` для Go-сервісу.
* **Захист вихідного коду:** у фінальний образ Node.js потрапляє виключно обфускований код (`javascript-obfuscator`) у каталозі `/app/dist` без вихідної папки `src` та `devDependencies`; Go-сервіс скомпільовано у єдиний статичний бінарний файл `/app/app` із прапорами `-ldflags="-s -w" -trimpath`.

## 5. Висновки

У ході виконання лабораторної роботи №8 було побудовано масштабовану та захищену мікросервісну інфраструктуру під керуванням Docker Compose. Використання **Nginx** як єдиного вхідного шлюзу забезпечило термінацію TLS по протоколу HTTP/2, кешування статичного й динамічного контенту, захист ендпоінтів автентифікації від brute-force атак (`429 Too Many Requests`) та безперебійну обробку запитів при виході з ладу окремої репліки (`failover`). Застосування multi-stage збірки образів, обфускації коду Node.js, статичної компіляції Go-сервісу та запуску процесів від непривілейованих користувачів дозволило мінімізувати поверхню атаки контейнерів і забезпечити надійну мережеву ізоляцію баз даних та внутрішніх сервісів.
