# Лабораторна робота 4. Побудова багаторівневої архітектури серверного застосунку

## 1. Мета роботи

Опанувати принципи проєктування серверних застосунків із багаторівневою архітектурою (**Router → Controller → Service → Repository → DataStore**) на платформах **Node.js (Express)** та **Go (`net/http`)**. Реалізувати ізоляцію бізнес-логіки від транспортного рівня та деталей збереження даних за допомогою інверсії залежностей (інтерфейси в Go та контракти репозиторію в Node.js), додати проміжне ПЗ (`middleware`) для логування й валідації запитів, побудувати централізовану систему обробки помилок та покрити рівні **Service** і **API** автоматизованими тестами.

## 2. Архітектура та структура проєктів

Обидва сервіси побудовані за єдиним потоком обробки HTTP-запитів із чітким розмежуванням відповідальностей між шарами:

```text
HTTP Request
     │
     ▼
┌──────────────────────┐
│ Middleware Pipeline  │  (Request Logging + Request Validation)
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│       Router         │  (Визначення маршрутів, HTTP-методів та підключення middleware)
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│     Controller       │  (Парсинг JSON, DTO-валідація, формування HTTP-відповідей)
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│       Service        │  (Бізнес-логіка та бізнес-правила, повністю незалежні від HTTP)
└──────────┬───────────┘
           │  abstraction (BookRepository interface / contract)
           ▼
┌──────────────────────┐
│      Repository      │  (InMemoryBookRepository — можливість заміни на DB без змін у Service)
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│      DataStore       │  (Потокобезпечне сховище даних у пам'яті)
└──────────────────────┘
```

## 3. Ізоляція шарів та інверсія залежностей

Ключовою вимогою лабораторної роботи є усунення жорсткої прив'язки бізнес-логіки (`Service`) до конкретного способу зберігання даних (`InMemoryRepository`), щоб у майбутньому можна було підключити реляційну чи документоорієнтовану БД (`DatabaseRepository`) без зміни коду сервісу:

* **У Go** визначено інтерфейс `repository.BookRepository` із методами `FindAll`, `FindByID`, `FindByTitleAndAuthor`, `Create`, `Update` та `Delete`. Структура `service.BookService` приймає цей інтерфейс у конструкторі `NewBookService(repo)`.
* **У Node.js** створено базовий контракт `BookRepository` та реалізацію `InMemoryBookRepository`, яка передається у `new BookService(bookRepository)` на етапі композиції застосунку в `app.js`.

## 4. Middleware та централізована обробка помилок

### 4.1. Реалізовані Middleware

1. **Request Logging (`logging.js` / `logging.go`):** фіксує HTTP-метод, шлях запиту, підсумковий HTTP-код відповіді та тривалість обробки у мілісекундах у форматі `GET /api/books/1 200 2ms`.
2. **Request Validation (`validation.js` / `validation.go`):** перехоплює некоректні запити ще до передачі на рівень бізнес-логіки — перевіряє валідність числового ідентифікатора `:id`, наявність заголовка `Content-Type: application/json`, обов'язковість рядкових полів `title` та `author`, а також коректність діапазону поля `year`.

### 4.2. Централізована обробка помилок

Замість дублювання формування відповідей про помилки у кожному ендпойнті використано єдиний механізм (`errorHandler` у Node.js та `apperror.WriteError` у Go), який повертає стандартизований JSON-об'єкт:

```json
{
  "error": "book_not_found",
  "message": "Book with id 999 was not found"
}
```

Підтримувані HTTP-коди помилок:
* **`400 Bad Request`** (`invalid_json`, `invalid_id`, `validation_error`, `unsupported_media_type`) — невалідний синтаксис JSON або некоректні вхідні параметри;
* **`404 Not Found`** (`book_not_found`, `route_not_found`) — запитуваний ресурс або маршрут не існує;
* **`409 Conflict`** (`book_already_exists`) — порушення бізнес-правила унікальності (спроба створити чи оновити книгу з уже наявною комбінацією `title + author`);
* **`500 Internal Server Error`** (`internal_server_error`) — непередбачена внутрішня помилка сервера.

## 5. Специфікація REST API та запуск

| HTTP-метод | Ендпойнт | Призначення | Код успіху | Коди помилок |
| :--- | :--- | :--- | :--- | :--- |
| `GET` | `/health` | Перевірка працездатності сервісу | `200 OK` | — |
| `GET` | `/api/books` | Отримати список усіх книг | `200 OK` | — |
| `GET` | `/api/books/:id` | Отримати книгу за ідентифікатором `id` | `200 OK` | `400`, `404` |
| `POST` | `/api/books` | Створити нову книгу | `201 Created` | `400`, `409` |
| `PUT` | `/api/books/:id` | Повністю оновити дані книги за `id` | `200 OK` | `400`, `404`, `409` |
| `DELETE` | `/api/books/:id` | Видалити книгу за `id` | `204 No Content` | `400`, `404` |

### Запуск серверів та тестів

* **Node.js (порт `3000`):**
  ```bash
  cd lab4/node-service
  npm install
  npm test      # запуск юніт- та API-тестів
  npm start     # запуск HTTP-сервера
  ```
* **Go (порт `8080`):**
  ```bash
  cd lab4/go-service
  go test -v ./tests/...     # запуск юніт- та API-тестів
  go run ./cmd/server        # запуск HTTP-сервера
  ```

## 6. Результати тестування

Для обох сервісів створено два рівні автоматизованих тестів:

1. **Service tests (ізольовані юніт-тести без запуску HTTP-сервера):**
   * перевірка створення нової книги;
   * перевірка бізнес-правила унікальності (повернення помилки `409 Conflict` при спробі додати дублікат);
   * перевірка пошуку існуючої книги та обробки відсутнього `id` (`404 Not Found`);
   * перевірка оновлення та видалення записів.
2. **API tests (інтеграційні тести HTTP-ендпойнтів):**
   * успішний `GET /api/books` (`200 OK`);
   * успішний `POST /api/books` (`201 Created`);
   * некоректний `POST` з порожніми полями або битим JSON (`400 Bad Request`);
   * дублюючий `POST` (`409 Conflict`);
   * `GET /api/books/999` для неіснуючого ресурсу (`404 Not Found`);
   * `DELETE` існуючого запису (`204 No Content`).

## 7. Висновки

Під час виконання лабораторної роботи сервіси каталогу книг на **Node.js** та **Go** було переведено на багаторівневу архітектуру з чітким розділенням зон відповідальності:

1. **Підтримуваність та масштабованість коду:** відокремлення `Router`, `Controller`, `Service` та `Repository` усунуло дублювання логіки та спростило додавання нових маршрутів і правил валідації.
2. **Незалежність бізнес-логіки:** використання інтерфейсу `BookRepository` у Go та базового класу-контракту з ін'єкцією залежностей у Node.js гарантує можливість заміни сховища у пам'яті на повноцінну базу даних без модифікації `BookService`.
3. **Тестованість:** ізоляція рівня `Service` від HTTP-транспорту дозволила перевіряти бізнес-правила та обробку граничних випадків без підняття мережевого сервера, а централізований обробник помилок забезпечив передбачуваний формат відповідей API.
