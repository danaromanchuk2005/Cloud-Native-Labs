# Лабораторна робота 3. Конкурентний pipeline обробки даних у Go

## 1. Мета роботи

Опанувати побудову конкурентних конвеєрів обробки даних (pipelines) у мові програмування **Go** із використанням типізованих каналів (`chan`), пулу воркерів (**Worker Pool**), примітивів синхронізації (`sync.WaitGroup`) та механізму скасування операцій (`context.Context` у поєднанні з оператором `select`). Дослідити вплив кількості воркерів і розміру буфера каналів на продуктивність та перевірити відсутність станів гонитви (data races) за допомогою вбудованого Race Detector.

## 2. Архітектура та реалізація pipeline

Застосунок реалізує класичну багатоетапну схему потокової обробки:

```text
Producer ──> [ jobs chan Job ] ──> Worker Pool (1..16 goroutines) ──> [ results chan Result ] ──> Aggregator ──> Output
```

### Ключові структури даних та компоненти:
* **`Job` та `Result`:** структури для передачі вхідного завдання (`ID`, `Value`) та результату обчислень (`JobID`, `Value`).
* **Обчислювальне навантаження (`compute`):** для кожної задачі обчислюється квадрат вхідного числа ($value^2$) у поєднанні з контрольованим циклом арифметичних операцій ($4 \cdot 10^4$ ітерацій) для моделювання CPU-bound обробки.
* **`Producer`:** генерує задану кількість задач (`-tasks`), передає їх у канал `jobs` із перевіркою `<-ctx.Done()` та гарантовано закриває канал (`defer close(jobs)`) після завершення генерації.
* **`Worker Pool`:** запускає конфігуровану кількість горутин-воркерів (`-workers`: $1, 2, 4, 8, 16$). Кожен воркер у циклі через `select` очікує або нову задачу з `jobs`, або сигнал скасування з `ctx.Done()`. Після закриття `jobs` і вичитування всіх елементів воркер зменшує лічильник `sync.WaitGroup` (`defer wg.Done()`).
* **Керування закриттям `results`:** окрема фонова горутина очікує завершення всіх воркерів (`wg.Wait()`) і закриває вихідний канал `close(results)`.
* **`Aggregator`:** вичитує всі результати з `results`, підраховує кількість оброблених задач (`Completed`), накопичує загальну суму (`TotalSum`) та фіксує повний час роботи конвеєра.

## 3. Перевірка синхронізації (`-race`) та скасування (`context.Context`)

### 3.1. Тестування на відсутність станів гонитви (Race Detector)
Запуск програми з прапорцем `-race`:
```bash
go run -race main.go -tasks 10000 -workers 8 -buffer 100
```
* **Результат:** `Completed: 10000 | TotalSum: 333383379897 | Time: 208.31 ms | Cancelled: false`.
* Попереджень `WARNING: DATA RACE` не виявлено, а контрольна сума `333383379897` збігається з точністю до одиниці в усіх запусках.

### 3.2. Перевірка коректного скасування через `context.Context` та `select`
Запуск $100\,000$ задач з обмеженням часу виконання у `30 мс`:
```bash
go run main.go -tasks 100000 -workers 4 -buffer 10 -timeout 30
```
* **Результат:** `Completed: 546 | TotalSum: 54412063 | Time: 30.66 ms | Cancelled: true`.
* Після спливання таймауту канал `ctx.Done()` закрився, що миттєво перервало роботу `Producer` та всіх горутин `Worker Pool` без витоку горутин чи взаємного блокування (deadlock).

## 5. Висновки

1. **Масштабування за кількістю воркерів:** При збільшенні кількості воркерів з `1` до `4` спостерігається практично лінійне прискорення обробки ($1301.76\text{ мс} \rightarrow 323.82\text{ мс}$, тобто у $4.02$ раза). Подальше збільшення до `8` та `16` воркерів продовжує скорочувати час виконання ($199.05\text{ мс}$ і $169.62\text{ мс}$ відповідно), але приріст стає сублінійним через досягнення фізичної межі продуктивних ядер процесора та витрати на планування горутин.
2. **Вплив буферизації каналів (`Buffer`):** Використання небуферизованих каналів (`Buffer = 0`) вимагає синхронного рандеву між `Producer`, воркерами та `Aggregator` на кожному повідомленні. Додавання буфера (`Buffer = 100`) при `8` воркерах зменшило час виконання зі `199.05 мс` до `186.52 мс` ($\approx 6.3\%$), згладивши піки затримок при передачі даних. Подальше збільшення буфера до `1000` вже не дає додаткового виграшу, оскільки обмежувальним фактором стають самі CPU-обчислення.
3. **Надійність та безпека конкурентності:** Комбінація `defer close(jobs)`, `sync.WaitGroup` для координації закриття `results` та `context.Context` у блоках `select` забезпечує детермінований результат (`TotalSum` стабільний в усіх тестах), відсутність гонитви даних (`-race`) та коректне аварійне завершення роботи конвеєра.
