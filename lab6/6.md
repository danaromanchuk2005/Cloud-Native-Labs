# Лабораторна робота 6. Рівень персистентності: Інтеграція SQL та NoSQL баз даних у Node.js та Go

## 1. Мета роботи

Розширити багаторівневу архітектуру серверних застосунків із попередніх лабораторних робіт реальним рівнем персистентності на базі реляційної СКБД **PostgreSQL** та документоорієнтованої СКБД **MongoDB** із використанням нативних драйверів (без ORM) для стеків **Node.js** та **Go**. Забезпечити повну ізоляцію бізнес-логіки (`Service` та `Controller`) від деталей сховища з можливістю перемикання БД через змінну оточення `REPO_TYPE`, реалізувати ACID-транзакції, модель **Polyglot Persistence**, а також інтегрувати рівень БД із **WebSocket-broadcast** та **Stream-експортом** даних.

## 2. Архітектура системи та структура проєкту

Застосунок зберігає чітке розділення відповідальностей (`Router → Controller → Service → Repository → DB`) та дозволяє підключати різні сховища даних без зміни бізнес-логіки:

## 3. Інфраструктура та налаштування пулів з'єднань

### 3.1. Docker Compose та конфігурація `.env`

За допомогою `docker-compose.yml` розгорнуто два контейнери з постійними томами (`pgdata`, `mongodata`):
* **`lab6-postgres` (`postgres:16-alpine`):** порт `5432`, автоматичне виконання `init.sql` для створення таблиць `users` (із обмеженням `email UNIQUE`) та `accounts`.
* **`lab6-mongo` (`mongo:7`):** порт `27017`, при старті застосунку створюється унікальний індекс `{ email: 1 }` для колекції `users` та використовується колекція `events` для журналювання подій.

Усі облікові дані винесено до файлу `.env` (доданого в `.gitignore`), а у репозиторії збережено шаблон `.env.example`.

### 3.2. Обґрунтування розмірів Connection Pool

* **Node.js (`max: 15` у `pg.Pool` та `maxPoolSize: 15` у `MongoClient`):** Node.js працює на базі однопотокового циклу подій (Event Loop) і виконує I/O-операції асинхронно. Оптимальний розмір пулу в діапазоні $10\text{–}20$ з'єднань дозволяє ефективно обслуговувати конкурентні запити без надмірного навантаження на сервери БД.
* **Go (`SetMaxOpenConns(30)` та `SetMaxPoolSize(30)`):** Go використовує легковагові паралельні горутини, кожна з яких може одночасно виконувати блокуючий SQL/NoSQL-запит. Розмір пулу $30$ з'єднань (у межах рекомендованих $25\text{–}50$) запобігає простоюванню горутин в очікуванні вільного сокета.

## 4. Реалізація ключових механізмів

### 4.1. Архітектурна ізоляція та перемикання `REPO_TYPE`

Клас `UserService` (Node.js) та структура `service.UserService` (Go) працюють виключно через абстракцію `UserRepository`. Перемикання між PostgreSQL та MongoDB відбувається зміною одного параметра `REPO_TYPE` у `.env` (`postgres` $\leftrightarrow$ `mongo`) без жодних змін у коді контролерів чи сервісу. Дублювання `email` в обох СУБД обробляється і перетворюється на HTTP-статус **`409 Conflict`**, а відсутній запис — на **`404 Not Found`**.

### 4.2. ACID-транзакції PostgreSQL

Функція переказу коштів (`POST /api/accounts/transfer`) вручну бере з'єднання з пулу (`pool.connect()` у Node.js, `db.BeginTx()` у Go), відкриває транзакцію (`BEGIN`), блокує рядки рахунків (`FOR UPDATE`), перевіряє достатність коштів, виконує списання та зарахування і фіксує зміни (`COMMIT`). При нестачі коштів або будь-якій помилці виконується **`ROLLBACK`**, а з'єднання гарантовано повертається в пул у блоці `finally` / `defer`.

### 4.3. Polyglot Persistence, WebSocket-broadcast та Stream-експорт

1. **Polyglot Persistence (`GET /api/events`):** незалежно від того, чи зберігаються користувачі в PostgreSQL (`REPO_TYPE=postgres`), чи в MongoDB (`REPO_TYPE=mongo`), усі події (`user_created`, `user_updated`, `user_deleted`) записуються в колекцію `events` у MongoDB.
2. **WebSocket-broadcast (`/ws`):** при кожній зміні користувача всі підключені WebSocket-клієнти миттєво отримують JSON-сповіщення про подію.
3. **Stream-експорт (`GET /api/users/export`):** вибірка користувачів з БД читається порціями (`batch`) через `Readable` stream, перетворюється у формат CSV через `Transform` stream і записується у файл `data/export.csv` через `Writable` stream з використанням `pipeline()` (автоматичний контроль **Backpressure**) та трансляцією прогресу `export_progress` у WebSocket.

### 5.1. Перемикання сховищ (`REPO_TYPE=postgres` $\rightarrow$ `REPO_TYPE=mongo`)

| Операція / Сценарій | Режим `REPO_TYPE=postgres` | Режим `REPO_TYPE=mongo` | Статус |
| :--- | :--- | :--- | :--- |

| `PUT /api/users/:id` (оновлення) | `200 OK` | `200 OK` | Успішно |
| `GET /api/users/export` (CSV Stream) | `200 OK`, експортовано 3 записи + WS-прогрес | `200 OK`, експортовано 1 запис + WS-прогрес | Успішно |
| `DELETE /api/users/:id` (видалення) | `204 No Content` | `204 No Content` | Успішно |

### 5.2. Перевірка транзакцій PostgreSQL та Polyglot Persistence

* **Успішний переказ (`amount: 150` з рахунку `1` на `2`):** статус `200 OK` (`committed`), баланси змінилися з `(1000, 500)` $\rightarrow$ `(850, 650)` $\rightarrow$ `(700, 800)`.
* **Переказ із перевищенням балансу (`amount: 999999`):** статус `400 Bad Request` (`insufficient_funds`), виконано `ROLLBACK`, баланси залишилися незмінними (`700` та `800`).
* **Журнал подій у MongoDB (`GET /api/events`):** зафіксовано всі `6` CRUD-подій із обох тестових прогонів.
* **Go unit-тести (`go test -v ./tests/...`):** `TestUserServiceWithInMemoryRepo` — `PASS` (`0.361 s`).

## 6. Висновки

1. **Ізоляція рівня доступу до даних:** використання єдиного контракту `UserRepository` та фабрики конфігурації дозволило перемкнути сервіс між реляційною БД (PostgreSQL) та документоорієнтованою БД (MongoDB) зміною одного рядка у `.env` без модифікації бізнес-логіки.
2. **Цілісність даних у транзакціях:** явне керування транзакціями (`BEGIN`, `FOR UPDATE`, `COMMIT`, `ROLLBACK`) гарантує атомарність фінансових переказів і коректне повернення з'єднань у пул.
3. **Поєднання підходів (Polyglot Persistence + Streams + WebSockets):** використання MongoDB для високошвидкісного логування подій разом із потоковим експортом даних і WebSocket-сповіщеннями забезпечує масштабованість та реактивність сучасного хмарного застосунку.
