# Лабораторна робота 5. Неблокуючий I/O у реальному часі: Node.js Streams, Backpressure та WebSockets

## 1. Мета роботи

Розширити багаторівневий вебсервер із попередньої лабораторної роботи механізмами неблокуючої потокової обробки великих обсягів даних (**Node.js Streams**: `Readable`, `Transform`, `Writable`, `pipeline`) та двонаправленої комунікації в реальному часі (**WebSockets**). Дослідити роботу механізму **Backpressure** при повільному споживачі як у файлових потоках, так і в WebSocket-з'єднаннях, а також реалізувати трансляцію прогресу обробки великого файлу підключеним клієнтам у реальному часі.

## 2. Архітектура системи та структура проєкту

Застосунок інтегрує нові модулі потокової обробки та WebSocket-менеджменту у багаторівневу структуру з Лабораторної роботи 4 зі збереженням розділення відповідальностей:

## 3. Потокова обробка великих файлів та керування розміром порцій

### 3.1. Генерація тестового джерела даних
Скрипт `scripts/generate-file.js` формує великий файл у форматі NDJSON (`data/books-events.ndjson`), використовуючи `fs.createWriteStream` із перевіркою результату `stream.write()` та очікуванням події `'drain'`:
* **Кількість записів:** $1\,200\,000$ JSON-рядків;
* **Розмір файлу:** $142.97\text{ МБ}$ ($149\,909\,696\text{ байтів}$);
* **Час генерації:** $0.35\text{ с}$ без завантаження всього файлу в оперативну пам'ять.

### 3.2. Конвеєр `Readable → Transform → Writable` і параметр `highWaterMark`
Для обробки файлу використано зв'язування потоків через `stream/promises.pipeline(readable, transform, writable)`:
1. **`Readable` (`fs.createReadStream`):** читає файл послідовними порціями (chunks).
2. **`Transform` (`BookLogTransform`):** коректно склеює розірвані на межі чанків рядки (`this.remainder`), парсить JSON-записи, фільтрує події за рейтингом ($\text{rating} \ge 4$), збагачує об'єкти полями `status: "PROCESSED"` і `priority`, а також формує статистику прогресу.
3. **`Writable` (`fs.createWriteStream`):** записує відфільтровані записи у вихідний файл `data/books-processed.ndjson`.

**Вплив параметрів на розмір порцій даних:**
* **`highWaterMark`** визначає граничний обсяг внутрішнього буфера потоку в байтах, після досягнення якого потік припиняє читати нові дані з джерела, доки споживач не звільнить буфер.
* Для стандартних `stream.Readable` / `stream.Transform` значення за замовчуванням становить $16\text{ КБ}$ ($16\,384\text{ байти}$), тоді як для `fs.createReadStream` — $64\text{ КБ}$ ($65\,536\text{ байтів}$).
* При `highWaterMark = 65536` файл обсягом $142.97\text{ МБ}$ ($1\,200\,000$ рядків, із яких $480\,000$ пройшли фільтр) був повністю оброблений за **$395.11\text{ мс}$**. Зменшення `highWaterMark` знижує пікове використання буферів, але збільшує кількість системних викликів `read`/`write` та перемикань контексту.

## 4. Дослідження механізму Backpressure (Сценарій A проти Сценарію B)

Для перевірки поведінки системи при повільному споживачі (`scripts/backpressure-bench.js`) змодельовано штучну затримку запису $3\text{ мс}$ на кожен $64\text{ КБ}$ чанк на ділянці даних обсягом $25\text{ МБ}$:
* **Сценарій A (без Backpressure):** `Readable` зчитує дані за подією `'data'` на максимальній швидкості диска без виклику `readable.pause()`, накопичуючи всі трансформовані буфери та відкладені задачі запису в пам'яті.
* **Сценарій B (із Backpressure):** використовується `pipeline()` зі стандартним сигналом зворотного тиску — коли буфер повільного `Writable` заповнюється понад `highWaterMark`, метод `.write()` повертає `false`, а `Readable` автоматично призупиняє читання до настання події `'drain'`.

| Метрика | Сценарій A (Без Backpressure) | Сценарій B (З Backpressure) | Порівняння |
| :--- | :---: | :---: | :--- |
| **Час виконання (`durationMs`)** | $1214.52\text{ мс}$ | $1350.99\text{ мс}$ | Синхронізація за темпом споживача |
| **Піковий RSS (`peakRssMB`)** | $91.92\text{ МБ}$ | $63.16\text{ МБ}$ | **$-28.76\text{ МБ}$** на користь Backpressure |
| **Приріст пам'яті RSS (`deltaRssMB`)** | $+28.51\text{ МБ}$ | $+8.32\text{ МБ}$ | Споживання пам'яті нижче у **$3.43\times$** |
| **Піковий V8 Heap (`peakHeapMB`)** | $8.71\text{ МБ}$ | $6.59\text{ МБ}$ | Стабільне використання купи без накопичення черги |

**Висновок із тесту:** без механізму Backpressure швидкий виробник миттєво вичитує дані й накопичує чергу в оперативній пам'яті (на гігабайтних файлах це призводить до помилки `JavaScript heap out of memory`). Увімкнений Backpressure утримує споживання пам'яті сталим незалежно від загального розміру файлу.

## 5. WebSocket-сервер, життєвий цикл та інтеграція зі Streams

### 5.1. Життєвий цикл клієнта та обробка подій
Модуль `WebSocketManager` (`ws://localhost:3000/ws`) зберігає реєстр активних підключень (`clientId`, `username`, `connectedAt`, `state`, `droppedMessages`) та підтримує повний цикл взаємодії:
1. **Connection:** реєстрація нового клієнта у стані `CONNECTED` та надсилання вітального пакета з призначеним `clientId`.
2. **Authentication / Identification:** обробка повідомлення `{"type": "auth", "username": "..."}`, переведення клієнта у стан `AUTHENTICATED` та сповіщення інших учасників (`user_joined`).
3. **Message Exchange & Validation:** прийом чат-повідомлень `{"type": "message", "text": "..."}` і розсилка (`broadcast`) усім іншим активним клієнтам. При отриманні битого JSON або невідомого типу повертається структурована помилка (`invalid_json`, `invalid_schema`, `unknown_type`) без падіння сервера.
4. **Close / Error:** очищення запису клієнта при закритті з'єднання або розриві сокета та розсилка події `user_left`.

### 5.2. Трансляція прогресу Streams у реальному часі та захист від повільного клієнта
Під час виконання `POST /api/streams/process` модуль `BookLogTransform` надсилає у `WebSocketManager` події прогресу (`{"type": "progress", "processed": ..., "total": ..., "percent": ...}`).

Для захисту сервера від необмеженого зростання буфера відправки (`ws.bufferedAmount`), якщо один із клієнтів перестає встигати зчитувати дані (`SlowClient-3` із призупиненим TCP-сокетом), реалізовано дворівневий захист:
1. **Message Dropping (`SOFT_BUFFER_LIMIT = 32 KB`):** якщо `ws.bufferedAmount` перевищує $32\text{ КБ}$, проміжні кадри `progress` (позначені як `droppable: true`) пропускаються для цього клієнта без затримки швидких споживачів.
2. **Connection Termination (`HARD_BUFFER_LIMIT = 256 KB`):** якщо черга клієнта перевищує критичний поріг $256\text{ КБ}$, сервер примусово закриває повільне з'єднання з кодом `1008` (`Slow consumer: buffer limit exceeded`).

## 6. Висновки

1. **Ефективність Node.js Streams:** потокова обробка файлу обсягом $142.97\text{ МБ}$ ($1\,200\,000$ записів) через зв'язку `Readable → Transform → Writable` виконується за $395.11\text{ мс}$ із мінімальним використанням оперативної пам'яті.
2. **Критичність Backpressure:** експериментально підтверджено, що без контролю швидкості споживача приріст пам'яті RSS на $25\text{ МБ}$ даних становить $+28.51\text{ МБ}$, тоді як стандартний механізм Backpressure (`pipeline` + `highWaterMark`) обмежує його до $+8.32\text{ МБ}$.
3. **Стійкість Real-Time WebSockets:** поєднання потокової обробки даних із WebSocket-розсилкою дозволяє інформувати клієнтів про прогрес тривалих операцій у реальному часі, а моніторинг `ws.bufferedAmount` із політикою відкидання проміжних кадрів захищає сервер від деградації через повільних клієнтів.
