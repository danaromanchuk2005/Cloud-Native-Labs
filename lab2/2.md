# Лабораторна робота 2. Дослідження моделей конкурентності та планування обчислень у Node.js та Go

## 1. Мета роботи

Дослідити відмінності між моделями конкурентності **Node.js** (однопотоковий Event Loop із неблокуючим I/O) та **Go** (M:N-планувальник легковагових потоків — `goroutines`). Проаналізувати поведінку обох платформ під час I/O-bound та CPU-bound навантаження, оцінити вплив важких обчислень на доступність службового ендпойнту `/health`, порівняти послідовне та паралельне виконання задач у Go та провести навантажувальне тестування.

## 2. Реалізовані ендпойнти

До базових сервісів із Лабораторної роботи 1 додано ендпойнти для імітації різних типів навантаження:

| HTTP-метод | Ендпойнт | Платформа | Опис реалізації |
| :--- | :--- | :--- | :--- |
| `GET` | `/io` | Node.js, Go | Імітація асинхронної I/O-операції тривалістю `100 мс` (`setTimeout` через `Promise` у Node.js та `time.Sleep` у Go). |
| `GET` | `/cpu` | Node.js | Синхронне виконання 4 циклів по $4 \cdot 10^8$ ітерацій (разом $1.6 \cdot 10^9$ інкрементів) в основному потоці Event Loop. |
| `GET` | `/cpu` | Go | Послідовне виконання 4 циклів по $4 \cdot 10^8$ ітерацій в одній горутині обробника HTTP-запиту. |
| `GET` | `/cpu/parallel` | Go | Паралельне виконання 4 циклів по $4 \cdot 10^8$ ітерацій у 4 окремих `goroutines` із синхронізацією через `sync.WaitGroup`. |

## 3. Експеримент 1. Вплив CPU-навантаження на доступність `/health`

Для перевірки блокування потоку виконання спочатку надсилався фоновий запит `GET /cpu`, а через `100 мс` — три послідовні запити `GET /health`.

| Запит | Node.js (час відповіді) | Go (час відповіді) | Пояснення поведінки |
| :--- | :--- | :--- | :--- |
| `Health #1` | **`0.354370 с`** (354.4 мс) | **`0.000485 с`** (0.49 мс) | У Node.js перший `/health` чекав завершення `/cpu` у черзі Event Loop; у Go він миттєво виконався в окремій горутині. |
| `Health #2` | **`0.000438 с`** (0.44 мс) | **`0.000318 с`** (0.32 мс) | Після звільнення потоку в Node.js час відповіді нормалізувався. |
| `Health #3` | **`0.000452 с`** (0.45 мс) | **`0.000257 с`** (0.26 мс) | Стабільна мінімальна затримка на обох платформах. |

**Висновок до експерименту 1:** У Node.js будь-яка тривала синхронна CPU-операція повністю блокує Event Loop — у цей момент сервер не здатний відповідати навіть на легкі перевірки `livenessProbe`/`readinessProbe` (`/health`). У Go планувальник витісняє та розподіляє горутини між потоками ОС, тому `/health` відповідає без затримок ($\approx 0.3\text{--}0.5\text{ мс}$).

## 4. Експеримент 2. Послідовні обчислення проти `goroutines` у Go

Порівняння часу виконання $1.6 \cdot 10^9$ ітерацій (4 задачі по $4 \cdot 10^8$) на багатоядерному процесорі Apple Silicon:

* **`GET /cpu` (послідовне виконання в 1 горутині):** `372.77 мс`
* **`GET /cpu/parallel` (паралельне виконання у 4 `goroutines`):** `101.59 мс`

**Висновок до експерименту 2:** Запуск незалежних обчислювальних задач в окремих `goroutines` зменшив час обробки одного запиту у **3.67 раза** завдяки одночасному залученню кількох фізичних ядер процесора.

## 5. Навантажувальне тестування (`autocannon`)

Тестування проводилося утилітою `autocannon` протягом `10 секунд` для кожного сценарію:
* Для **I/O-навантаження** (`/io`, затримка $100\text{ мс}$): `50` одночасних з’єднань (`-c 50 -d 10`).
* Для **CPU-навантаження** (`/cpu` та `/cpu/parallel`): `10` одночасних з’єднань (`-c 10 -d 10`).

### Порівняльна таблиця результатів

| Workload | Runtime | RPS | Avg | p95 | p99 | CPU | RAM |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **I/O** | **Node.js** | `485` | `101.95 ms` | `104 ms` | `109 ms` | `~18%` | `~58 MB` |
| **I/O** | **Go** | `490` | `101.11 ms` | `103 ms` | `107 ms` | `~9%` | `~15 MB` |
| **CPU** | **Node.js** | `2.21` | `3550.10 ms` | `8110 ms` | `8110 ms` | `98.8%` | `76.7 MB` |
| **CPU (seq)** | **Go** | `18.20` | `532.36 ms` | `612 ms` | `619 ms` | `818.5%` | `20.8 MB` |
| **CPU (goroutines)** | **Go** | `19.40` | `505.64 ms` | `620 ms` | `771 ms` | `~825%` | `~21.5 MB` |

*(Примітка: у macOS показник `CPU = 818.5%` для процесу Go означає паралельну утилізацію понад 8 ядер процесора одночасно, тоді як однопотоковий процес Node.js обмежений одним ядром — `98.8%`).*

## 6. Загальні висновки

1. **Ефективність на I/O-bound задачах:** Обидві платформи демонструють практично однакову пропускну здатність (`485 RPS` у Node.js проти `490 RPS` у Go) та мінімальний оверхед поверх базової затримки в $100\text{ мс}$ (`Avg` $101.95\text{ мс}$ та $101.11\text{ мс}$ відповідно). Event Loop у Node.js і неблокуючі горутини в Go однаково добре справляються з великою кількістю паралельних мережевих очікувань, проте Go споживає приблизно у **3.7 раза менше оперативної пам’яті**.
2. **Поведінка на CPU-bound задачах:** При 10 одночасних CPU-запитах Node.js обробив лише `2.21 RPS` із середньою затримкою `3.55 с` (і `p99` понад `8.1 с`), оскільки всі запити ставали в чергу до одного ядра (`CPU 98.8%`, `RAM 76.7 MB`). Go завдяки багатопотоковому планувальнику задіяв усі доступні ядра (`CPU 818.5%`), забезпечив понад **у 8 разів вищу пропускну здатність** (`18.2–19.4 RPS`), стабільно низьку затримку (`~505–532 мс`) та спожив лише `20.8 MB` RAM.
3. **Практичне значення для Cloud Native:**
   * **Node.js** оптимальний для API-шлюзів, BFF (Backend for Frontend) та I/O-інтенсивних сервісів, де критична швидкість розробки, але важкі обчислення потрібно виносити у Worker Threads або окремі черги задач.
   * **Go** є кращим вибором для високонавантажених мікросервісів зі змішаним або CPU-інтенсивним профілем навантаження, оскільки ефективно утилізує виділені в Kubernetes vCPU-ліміти та має мінімальний footprint пам’яті.
